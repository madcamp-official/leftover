> 원래 따로 있던 `GETTING_STARTED.md`(실행 방법 중심)와 이 문서(구동 원리 중심)는 내용이
> 대부분 겹쳐서 하나로 합쳤다. [`우가우가게임_기획_프롬프트.md`](우가우가게임_기획_프롬프트.md),
> [`README.md`](../README.md), [`shared/PROTOCOL.md`](../shared/PROTOCOL.md),
> [`vision-server/README.md`](../vision-server/README.md)와 `pc-game/Assets/Scripts/GameFlow/`
> (`MatchController.cs`, `HubController.cs`) 코드를 바탕으로 "무엇을 어떻게 실행하고, 게임이
> 실제로 어떻게 돌아가는지"를 한 곳에 모은다. 미니게임 개별 규칙은 [`minigames/`](minigames/) 참고.

기획: [우가우가게임_기획_프롬프트.md](우가우가게임_기획_프롬프트.md). 두 사람이 각자 카메라
앞에서(P1/P2) 5개 미니게임을 순서대로 1판씩 겨루고, 더 많이 이긴 사람이 최종 승자(원래
있던 자세따라하기는 구현 난이도 문제로 폐기됨).

## 1. 큰 그림: 무엇이 어디서 실행되는가

- **Unity(`pc-game`)는 PC 한 대에서만 실행**된다. 두 사람은 그 화면 하나를 같이 보면서
  플레이한다 — 화면이 둘로 나뉘어 각자 다른 화면을 보는 로컬 스플릿스크린도, 진짜
  분산 렌더링도 아니다.
- **입력(카메라 인식)은 플레이어 1명당 별도 프로세스**(`vision-server`, Python)로 돈다.
  Unity를 실행하는 PC 자체에서 한 명분을 같이 돌려도 되고(`--pc-ip 127.0.0.1`), 완전히
  다른 노트북 2대에서 각각 돌려도 된다.
- Unity와 vision-server 사이는 **UDP 9100, 같은 LAN 안에서만** 통신한다(포트/방향은
  아래 3장). 진짜 원격지(다른 장소) 플레이는 이번 범위 밖 — 방코드 기반 릴레이 서버로
  확장하는 설계는 [`배포_아키텍처_설계.md`](배포_아키텍처_설계.md)에 정리했고 아직 구현은
  없다.

```
[카메라 A, P1 노트북] → vision-server --player-id p1 ──┐
[카메라 B, P2 노트북] → vision-server --player-id p2 ──┤ UDP 9100 (같은 LAN)
                                                          ↓
                                         pc-game(Unity 2D, PC 한 대에서만 실행)
                                         → 두 사람이 이 화면을 같이 봄
```

## 2. "멀티플레이"의 실체 — 로컬 협업 관전 + 분산 입력

이 프로젝트에서 "멀티플레이"는 네트워크로 게임 상태를 동기화하는 멀티플레이가 아니라,
**입력 소스만 두 대의 카메라/PC로 분산**시키고 게임 로직·렌더링은 Unity 프로세스 하나에
집중시키는 구조다.

- 게임 상태(점수, 라운드 진행, 승패)는 전부 Unity 프로세스 하나(`MatchController`) 안에서만
  관리된다. Unity 인스턴스가 두 개 뜨서 서로 상태를 동기화하는 게 아니다.
- vision-server는 게임 상태를 전혀 모른다 — 그냥 "지금 이 카메라에 잡힌 사람의 관절
  좌표/표정 값"을 매 프레임 쏘기만 하는 단방향 스트리밍 클라이언트다. 어떤 미니게임이
  진행 중인지, 누가 이기고 있는지 같은 건 vision-server 쪽에서 알 필요도 없고 알지도 못한다.
- 초기 설계는 "웹캠 한 대 앞에 두 사람이 같이 서서 화면 좌/우로 구분"이었지만, 실측 결과
  두 사람이 붙어 있으면 사람 감지 단계에서 한쪽이 억제(NMS)되어 인식이 아예 안 되는 문제가
  나와서 **온라인 모드(플레이어 1명당 카메라 1대)를 기본으로 전환**했다. 카메라 1대짜리
  구모드(좌우를 hip 좌표 이력 기반으로 자동 구분)는 노트북이 한 대뿐일 때 빠른 테스트용으로만
  남아있다.

### 온라인 모드 vs 구모드

| | 온라인 모드 (권장/기본) | 구모드 |
|---|---|---|
| 카메라 대수 | 플레이어당 1대 (총 2대) | 1대에 두 사람 |
| 실행 인자 | `--player-id p1` / `p2` 지정 | `--player-id` 생략 |
| 좌/우 구분 방법 | 애초에 프레임에 한 명만 잡히므로 구분 불필요 — 실행 인자로 id 고정 | 직전 프레임 hip 중심 x좌표에 가장 가까운 쪽으로 매칭(이력 기반), 최초엔 왼쪽=p1/오른쪽=p2 |
| 알려진 문제 | 없음 (붙어서 서는 상황 자체가 없음) | 두 사람이 붙어 있으면 사람 감지 NMS가 한쪽을 억제해 인식 누락 발생 가능(신뢰도 임계값 0.5→0.3으로 낮춰도 완전 해소는 안 됨) |
| 용도 | 데모/실제 플레이 기본값 | 노트북 한 대뿐일 때 빠른 단독 테스트 |

와이어 포맷(JSON 스키마)은 두 모드에서 동일 — Unity 쪽(`PoseStreamReceiver`/`PoseInputHub`)은
어느 모드로 오든 코드 수정 없이 그대로 받는다.

## 3. LAN 연결 설정 방법

```bash
# vision-server 쪽 공통 준비 (각 노트북에서)
cd vision-server
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
# models/pose_landmarker_lite.task 는 레포에 커밋됨
# models/face_landmarker.task 는 없으면 README의 curl 명령으로 받아야 함
#  (없어도 서버는 안 죽지만 입벌림/눈감김 값이 계속 기본값 - 눈빛싸움/과일따기/돌바나나가 제대로 안 됨)
```

```bash
# 노트북 A (플레이어 1) — <Unity PC의 LAN IP>는 ipconfig/ifconfig로 확인
python main.py --pc-ip <Unity PC의 LAN IP> --player-id p1

# 노트북 B (플레이어 2)
python main.py --pc-ip <Unity PC의 LAN IP> --player-id p2
```

- 두 노트북과 Unity PC는 **같은 공유기/핫스팟(같은 LAN)** 에 있어야 한다.
- Unity PC 방화벽이 UDP 9100 인바운드를 막고 있으면 다른 노트북에서 온 패킷이 안 들어온다 —
  Windows는 "Windows Defender 방화벽 > 고급 설정"에서 인바운드 규칙을 추가해야 할 수 있다.
- Unity PC 자체에서 한 명분을 같이 돌리는 경우 `--pc-ip 127.0.0.1 --player-id p1`로 실행하면
  노트북은 한 대만 더 있으면 된다.
- `PoseStreamReceiver.cs`는 이미 모든 인터페이스(`IPAddress.Any`)에서 9100을 수신하므로 Unity
  쪽은 온라인 모드 대응을 위해 따로 손댈 게 없다.
- Unity 쪽: `Assets/Scenes/Hub.unity`를 열고 Play → "시작" 버튼.

## 4. 통신 프로토콜 요약 (자세한 스키마는 `shared/PROTOCOL.md`)

- **포트**: UDP 9100, 방향은 `vision-server → Unity`만(단방향, Unity→server 역방향 통신 없음).
- **전송 방식**: 이산적인 "인식된 동작 이벤트"가 아니라, **관절 좌표를 매 프레임 그대로
  스트리밍**한다. 분류/판정은 vision-server가 하지 않고 전부 Unity 쪽(게임팀)이 게임별
  임계값으로 직접 해석한다. 전송 주기는 별도 목표 없이 웹캠 캡처+추론 루프 속도 그대로
  (대략 15~30fps).
- **메시지 구조**:
  ```json
  { "t": 1721234567.123, "players": [ { "id": "p1", "pose": {...13개 관절...}, "face": {"mouthOpenRatio":0.08, "eyeAspectRatio":0.29} } ] }
  ```
  - `pose`: `nose`, `left/rightShoulder`, `left/rightElbow`, `left/rightWrist`,
    `left/rightHip`, `left/rightKnee`, `left/rightAnkle` — 13개, 전부 필수. 좌표는 MediaPipe
    정규화 이미지 좌표(x: 0~1 왼→오, y: 0~1 위→아래, z 없음).
  - `face`: `mouthOpenRatio`(0=다묾, 클수록 크게 벌림), `eyeAspectRatio`(뜬 눈 0.25~0.35,
    감으면 0.1 이하로 급락) — vision-server가 미리 계산해서 얹어 보내는 유일한 2개 값.
  - 사람이 안 잡히면 `players`가 빈 배열로 온다 — Unity는 이전 프레임 값을 유지하다가 일정
    시간(기본 0.5초) 이상 안 보이면 "연결 끊김"으로 취급해야 한다.
  - 온라인 모드에서는 두 vision-server 인스턴스가 각자 `players`에 자기 담당 플레이어 한 명만
    담아 같은 포트로 보내고, `PoseInputHub.ApplyFrame()`이 들어온 id만 갱신하는 구조라 두
    스트림이 자연스럽게 합쳐진다(Unity 쪽에서 포트/소스를 분리할 필요 없음).
- **Unity 수신부**: `PoseStreamReceiver.cs`가 파싱 → `PoseInputHub`에 반영. 개별 미니게임은
  UDP/JSON을 몰라도 되고 `PoseInputHub.GetPlayer(PlayerId.P1)` 등 정리된 API만 사용한다.
  vision-server가 안 켜져 있어도 `PoseInputHub.Instance.ApplyFrame(...)`을 직접 호출해 가짜
  데이터를 넣으면 미니게임 로직을 독립적으로 테스트할 수 있다.

## 5. 게임 내부 이벤트/씬 흐름 (`MatchController` / `HubController`)

```
Hub 씬(시작 화면)
  └─ "시작" 버튼 클릭 → MatchController.StartMatch()
       (CurrentRoundIndex = -1, P1Wins = P2Wins = 0 로 리셋)
        │
        ▼
     LoadNextRound() 반복 호출 ── RoundScenes 순서대로 씬 전환
       ["StoneThrow", "FruitJump", "CoconutCrack", "StoneOrBanana", "StaringContest"]
       (기획 중인 [소리지르기](minigames/07_소리지르기.md)·[깃털날기](minigames/08_깃털날기.md)는
       아직 씬이 없어 이 배열에 들어있지 않다 — 구현되면 여기에 추가할 것. 원래 있던
       "PoseCopy"는 자세따라하기 게임 폐기로 이 배열에서 제거됨)
        │  각 미니게임 씬 안에서: 승패가 갈리는 순간 딱 한 번
        │  MatchController.ReportRoundResult(winner)  (winner: P1 / P2 / null=무승부)
        │  → 이후 미니게임이 자체적으로 다음 라운드로 자동 진행하거나 버튼 대기
        ▼
     5개 씬을 모두 돌면 CurrentRoundIndex >= RoundScenes.Count → HubSceneName("Hub")으로 복귀
        │
        ▼
Hub 씬(결과 화면) — MatchController.IsMatchComplete == true
  └─ OverallWinner(): P1Wins/P2Wins 비교해서 승자 텍스트 표시(동점이면 "무승부")
  └─ "다시하기" 버튼 → StartMatch() 재호출로 처음부터 다시 시작
```

핵심 설계 포인트:

- `MatchController`는 씬을 넘나들어야 해서 `DontDestroyOnLoad` 싱글턴이다. 미니게임 씬은
  "누가 이겼는지"만 알려주면(`ReportRoundResult`) 되고, 다음 씬 로드/최종 집계는 전부
  `MatchController`가 책임진다 — 미니게임팀은 씬 전환 로직을 직접 구현할 필요가 없다.
- 씬 전환은 `SceneFadeTransition.TryLoadScene(nextScene)`을 통해 이루어지며, 중복 호출(더블
  클릭 등)로 라운드 인덱스가 두 번 증가하지 않도록 로드 성공 시에만 인덱스를 올린다.
- `HubController`는 시작 화면과 결과 화면을 겸한다 — `CurrentRoundIndex < 0`(아직 시작 안 함)
  이면 시작 화면, `IsMatchComplete`면 결과 화면을 보여주는 식으로 같은 Hub 씬 안에서
  상태에 따라 분기한다.
- `GameBootstrap.EnsureInputSystems()` / `EnsureMatchController()`가 각 씬 진입 시 필요한
  싱글턴(`PoseInputHub`, `MatchController` 등)을 자동으로 만들어주므로, 미니게임 씬 하나만
  단독으로 열어 Play해도(`Assets/Scenes/<게임이름>.unity`) 정상 동작한다.

## 6. 전체 실행 절차 요약

1. **vision-server 준비**: 두 사람이 각자(또는 한 명은 Unity PC에서) `python main.py --pc-ip
   <Unity PC의 LAN IP> --player-id p1`/`p2` 실행. 카메라 프리뷰 창에 랜드마크가 그려지면 정상.
2. **Unity 실행**: Unity PC에서 `Assets/Scenes/Hub.unity`를 열고 Play.
3. **시작**: Hub 화면에서 "시작" 버튼 → 5개 미니게임이 `RoundScenes` 순서대로 자동 진행되며,
   매 라운드 종료 시 승자가 `MatchController`에 누적된다.
4. **종료**: 5판이 끝나면 Hub 씬으로 복귀해 최종 스코어(`P1Wins : P2Wins`)와 승자를 보여주고,
   "다시하기"로 처음부터 재시작할 수 있다.

## 7. 막히면 (트러블슈팅 요약)

- `PoseInputHub.Instance`가 `null` → 씬에 `GameBootstrap.EnsureInputSystems()` 호출 코드가
  있는지 확인(각 미니게임 `Start()`에 이미 포함).
- UDP 9100으로 아무것도 안 옴 → vision-server 콘솔에 전송 로그가 있는지, Unity Console에
  바인딩 실패 경고가 없는지, 온라인 모드라면 Unity PC 방화벽이 UDP 9100 인바운드를 막고
  있지 않은지 확인.
- 눈 감김/입 벌림 값이 계속 기본값(0.3 / 0.0) → `face_landmarker.task` 모델 파일 누락 —
  `vision-server/README.md` "모델 파일" 참고해서 받을 것.
- vision-server 없이도 Unity는 켜지지만, 전 게임이 모션 기반이라 실질적으로는 vision-server
  없이는 플레이 불가(키보드 폴백 없음) — 필요하면 `PoseInputHub.Instance.ApplyFrame(...)`을
  호출하는 테스트용 디버그 스크립트를 임시로 추가해야 한다.

## 8. 호스트-클라이언트 분산 구조 (진행 중)

지금 1~7장은 "Unity 한 대 + 공용 화면" 기준 구동 방식이다. 이걸 **한쪽 PC(호스트)가 게임
시뮬레이션 전체를 돌리고, 다른 쪽(클라이언트)은 그 결과만 받아 화면에 그리는** 구조로 바꾸는
설계 원칙은 [`멀티플레이_분산_아키텍처_설계.md`](멀티플레이_분산_아키텍처_설계.md)에 정리되어
있다. 배포/스팀/백엔드 관련 논의는 **게임이 이 구조로 먼저 완성된 뒤에나 의미가 있으므로
후순위로 미룬다** — 지금은 로컬(LAN) 기준 분산 구조 완성에만 집중한다. 그 다음 단계로
"실행파일 하나 + 방코드로 인터넷 연결"을 어떻게 만들지는
[`배포_아키텍처_설계.md`](배포_아키텍처_설계.md)에 미리 설계만 정리해뒀다.

### 지금까지 구현된 것

- `Assets/Scripts/Network/`(`NetworkSession`, `GameEventChannel`, `NetworkTypes`) — TCP 게임
  이벤트 채널(9200번 포트), 호스트 대기/클라이언트 접속, 하트비트 기반 끊김 감지, 시계 오프셋
  추정용 핑퐁.
- `MatchController`가 역할을 인지해서 동작한다: **호스트/오프라인**은 기존과 동일하게 로컬
  판단으로 매치 시작/라운드 전환/결과 집계를 하고, 호스트는 그 시점마다 이벤트
  (`match_start`/`load_round`/`round_result`)를 브로드캐스트한다. **클라이언트**는 자기
  판단으로 아무것도 결정하지 않고, 저 세 이벤트를 받아서 로컬 상태(점수/라운드 인덱스)만
  똑같이 반영한다 — 그래서 `HubController` 같은 UI 코드는 호스트/클라이언트 구분 없이 그대로
  동작한다.
- Hub 화면(시작 화면)에 네트워크 모드 패널이 추가됐다 — "호스트로 시작"(내 IP 표시)
  / IP 입력 후 "접속" / "오프라인"(기본, 기존과 동일하게 로컬 단독 실행). 클라이언트
  역할일 때는 "시작" 버튼이 비활성화된다(매치 시작은 호스트만 트리거).

### 아직 안 된 것 (다음 단계)

**미니게임 내부(`Assets/Scripts/Minigames/*`)는 아직 이 구조를 모른다.** 지금은 클라이언트로
접속해도 각 미니게임 씬은 예전 그대로 로컬에서 자체 타이머/판정을 돌린다 — 클라이언트 쪽
카메라 입력이 호스트로만 가므로(아래 참고) 클라이언트 화면에서는 사람 인식 없이 타이머만
흘러가는 것처럼 보인다. 미니게임을 "호스트가 판정하고 이벤트로 알려주면 클라이언트는 그
이벤트를 재생만 하는" 구조로 바꾸는 작업이
[`멀티플레이_분산_아키텍처_설계.md` 4장·9장](멀티플레이_분산_아키텍처_설계.md#4-미니게임-스크립트-구조--simulaterender-분리)에
정리된 다음 단계다.

### 호스트-클라이언트로 실행하는 방법 (현재 기준)

1. 두 PC 모두 `Assets/Scenes/Hub.unity`를 열고 Play.
2. 한쪽에서 "호스트로 시작" 클릭 → 화면에 표시되는 IP를 다른 쪽에 알려준다.
3. 다른 쪽은 그 IP를 입력하고 "접속" 클릭 → "호스트에 연결됨" 표시되면 연결 완료.
4. **두 vision-server 모두 호스트 PC의 LAN IP로 `--pc-ip`를 지정**해서 실행한다
   (`python main.py --pc-ip <호스트 PC IP> --player-id p1` / `p2`) — 클라이언트 PC는
   카메라를 켜서 인식만 하고, 인식 결과는 클라이언트를 거치지 않고 바로 호스트로 간다.
5. 호스트에서 "시작" 클릭 → 양쪽 Hub 화면이 동시에 사라지고 첫 미니게임 씬으로 전환된다.
   (단, 위 "아직 안 된 것"대로 미니게임 자체의 판정/타이머 동기화는 아직 미완성.)
