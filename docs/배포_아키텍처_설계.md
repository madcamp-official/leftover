# 배포 아키텍처 설계 — 단일 실행파일, LAN 전용 (설계 단계, 미구현)

> **상태: 설계만 있고 구현 없음.** 지금 레포가 실제로 어떻게 동작하는지는
> [`게임_구동방식_정리.md`](게임_구동방식_정리.md) 1~7장(로컬 LAN, Unity 한 대)과 8장 +
> [`멀티플레이_분산_아키텍처_설계.md`](멀티플레이_분산_아키텍처_설계.md)(호스트-클라이언트
> 분산 구조, 구현 진행 중이나 LAN 전제)에 정리되어 있다. 이 문서는 그 다음 단계 — **실행파일
> 하나에 카메라/마이크 입력까지 전부 담아서, 같은 와이파이에 있는 두 사람이 IP만 입력하면
> 바로 플레이할 수 있는 배포 형태**를 어떻게 만들지에 대한 설계다.
>
> **범위 결정(중요)**: 이 게임의 강점은 같은 공간에서 마주 보고 즐기는 1:1 대면 플레이의
> 재미와 게임성이지, 원격/인터넷 배포 자체가 아니다. 그래서 **인터넷 너머 연결, 방코드
> 매치메이킹, 릴레이 서버는 이 프로젝트 범위에서 뺀다** — 서버를 새로 마련하고 운영/비용을
> 떠안을 이유가 없다. 목표는 딱 하나: **"두 사람이 같은 와이파이(공유기)에 있으면 실행파일
> 하나로 바로 플레이"**. (이전 버전 문서에 있던 방코드+릴레이 서버 설계는 이 결정으로
> 폐기했다 — 필요해지면 과거 git 히스토리에서 다시 꺼내올 수 있다.)
>
> **선행 조건**: 이 문서의 작업은
> [`멀티플레이_분산_아키텍처_설계.md`](멀티플레이_분산_아키텍처_설계.md)의 로컬 LAN
> 호스트-클라이언트 구조가 실제 2대 플레이로 검증된 뒤에 시작한다.

## 0. 목표와 현재 상태의 격차

목표: Windows/macOS용 실행파일(설치 프로그램 또는 단일 exe/app) 하나를 두 사람이 각자
노트북에 받아서 실행 → 같은 와이파이(공유기)에 연결 → 한쪽이 "호스트로 시작"을 누르면
IP가 화면에 뜨고 → 다른 쪽이 그 IP를 입력하면 연결되어 게임 시작. 카메라/마이크 캡처도 그
실행파일 안에서 자동으로 처리(별도 프로그램 실행 불필요).

지금과의 격차:

| 항목 | 지금 | 목표 |
|---|---|---|
| 실행 단위 | Unity 게임 + Python(`vision-server`) **두 프로세스**를 사람이 각자 수동 실행 | 실행파일 1개 |
| 연결 방식 | 호스트가 자기 LAN IP를 확인해서 알려주고, 클라이언트가 입력 | **이미 목표와 같음** — 그대로 재사용, 자동 탐색은 선택적 개선 |
| 네트워크 범위 | 같은 공유기/핫스팟(LAN) | **이미 목표와 같음** — 인터넷 확장은 하지 않기로 결정 |
| 카메라/마이크 | `vision-server`(Python/MediaPipe)가 캡처, Unity와 별개 프로세스 | 게임 실행파일 자체가 캡처(자동 실행) |

표를 보면 "연결 방식"과 "네트워크 범위"는 사실 **이미 목표와 같다** — LAN 안에서 IP로
직접 붙는 구조는 [`멀티플레이_분산_아키텍처_설계.md`](멀티플레이_분산_아키텍처_설계.md)에서
이미 설계·구현 중이다. 이 문서가 실제로 다루는 건 딱 하나, **"Unity + Python 두 프로세스를
사람이 따로 켜야 하는" 문제를 실행파일 하나로 합치는 패키징 작업**뿐이다. 서버가 아예
필요 없으므로 방코드 발급, 매치메이킹, NAT 통과 같은 문제 자체가 생기지 않는다.

## 1. 방식 A — vision-server를 게임 실행파일에 번들링 (채택)

MediaPipe 추론을 Unity(C#) 쪽으로 완전히 이식하는 대신, **이미 검증된 `vision-server`
(Python/MediaPipe) 코드를 그대로 두고 게임 실행파일이 그걸 백그라운드 프로세스로 감싸서
자동 실행/종료**한다. 프로토콜(`shared/PROTOCOL.md`, UDP 9100/9101)은 전혀 안 바뀐다 —
지금 vision-server가 `--pc-ip 127.0.0.1`로 보내는 것과 동일하게, 그냥 그 대상 프로세스를
사람이 터미널에서 켜는 대신 게임이 대신 켜줄 뿐이다.

- **패키징**: `vision-server`를 PyInstaller 등으로 OS별(Windows/macOS) 단일 실행 바이너리로
  빌드하고, 모델 파일(`models/*.task`)과 함께 Unity 빌드 결과물 옆에 동봉한다(Windows는
  `StreamingAssets` 옆 폴더, macOS는 `.app` 번들 내부 `Resources`).
- **자동 실행**: Unity가 게임 시작 시(Hub 씬에서 역할이 정해지는 시점) 이 바이너리를
  `System.Diagnostics.Process.Start`로 실행하고, `--pc-ip 127.0.0.1 --player-id p1`처럼
  로컬호스트로 인자를 넘긴다. 카메라/마이크 OS 권한 프롬프트는 이 서브프로세스 최초 실행
  시 한 번 뜨는데, 처음 켤 때 "카메라/마이크 접근 허용" 안내를 게임 UI에서 먼저 보여줘야
  프로세스가 죽은 것처럼 보이지 않는다.
- **생명주기**: 게임 종료(`OnApplicationQuit`) 시 서브프로세스도 함께 종료한다. 비정상
  종료(강제 종료, 크래시) 대비로 부모 프로세스 감시(부모 PID가 죽으면 자식도 종료) 로직이
  필요 — 자세한 값은 4장 TODO.
- **왜 이 방식인가**: MediaPipe를 Unity Sentis/Barracuda로 완전히 재구현하는 방식(검토했던
  대안)은 정확도·개발 기간 둘 다 리스크가 커서, 검증된 Python 코드를 그대로 감싸는 이
  방식을 채택한다. "진짜 하나의 코드베이스"는 아니지만 "사용자 입장에서 실행파일 하나"라는
  목표는 이걸로 충분히 달성된다.

## 2. LAN 연결 — 기존 구조를 그대로 재사용

방코드/릴레이 서버를 빼기로 했으므로, 연결 자체는
[`멀티플레이_분산_아키텍처_설계.md` 5장](멀티플레이_분산_아키텍처_설계.md#5-이벤트-채널--tcp-json-라인)에
있는 지금 구조(`GameEventChannel` TCP, 호스트가 IP를 화면에 띄우고 클라이언트가 그 IP를
입력)를 **그대로 배포판에도 쓴다.** 추가로 손댈 게 원칙적으로 없다 — 로컬 LAN 구조가
실제 2대 플레이로 검증만 되면 배포판에서도 동일하게 동작한다.

### 2.1 선택적 개선 — LAN 자동 탐색 (필수 아님)

IP를 직접 입력하는 대신, 같은 와이파이 안에서 상대를 자동으로 찾아주면 UX가 더 매끄럽다.
구현한다면:

- 호스트가 "호스트로 시작"을 누르면 로컬 UDP 브로드캐스트(예: 포트 9201)로 "나 여기
  있음"을 주기적으로 뿌린다.
- 클라이언트는 같은 서브넷에서 그 브로드캐스트를 듣고 있다가 잡히면 자동으로 호스트 IP를
  채워 넣는다(또는 발견된 호스트 목록을 보여주고 선택하게 한다).
- 이건 순수 UX 개선이라 **1장(vision-server 번들링)보다 우선순위가 낮다.** IP 직접
  입력만으로도 기능적으로는 완성된 배포다.

### 2.2 이 구조가 하지 않는 것

- **인터넷 너머 연결을 지원하지 않는다.** 같은 공유기/핫스팟에 있지 않으면 애초에
  IP로 서로를 못 찾는다 — 이건 버그가 아니라 이번 범위 결정에 따른 의도된 제약이다.
- **서버를 두지 않는다.** 방 생성/매치메이킹/중계를 하는 별도 프로세스가 없으므로
  운영·비용·가동 부담이 아예 없다.

## 3. 빌드/배포 파이프라인 (개요, 미착수)

- **Unity 빌드**: `File > Build Settings`로 Windows(x64)/macOS(Universal) 빌드. 지금까지는
  Editor에서 Play로만 실행해봤고 Standalone 빌드 자체가 아직 한 번도 검증되지 않았다 —
  1장 작업 이전에 **일단 지금 구조(로컬 LAN) 그대로 Standalone 빌드가 되는지부터
  확인**하는 게 먼저다(빌드 시 누락되는 리소스, `PoseInputHub` 등 싱글턴 초기화 순서 문제
  등은 Editor에서는 안 드러날 수 있음).
- **vision-server 바이너리 동봉**: 1장의 PyInstaller 산출물을 Unity 빌드 폴더 구조에 맞게
  복사하는 빌드 후처리 스크립트가 필요.
- **코드사이닝/공증**: macOS는 Gatekeeper 통과를 위한 Apple Developer 서명·공증, Windows는
  SmartScreen 경고 완화를 위한 코드 서명 인증서가 있으면 좋지만, 몰입캠프 데모 규모에서는
  없어도 "고급 정보 → 실행"으로 우회 가능 — 우선순위 낮음.
- **설치 배포 방식**: zip 압축 해제형으로 시작(가장 단순), 필요하면 이후 인스톨러(Windows:
  Inno Setup 등, macOS: dmg) 검토.

## 4. 단계별 진행 순서 제안

1. **(선행)** [`멀티플레이_분산_아키텍처_설계.md`](멀티플레이_분산_아키텍처_설계.md)의
   로컬 LAN 호스트-클라이언트 구조를 실제 2대 플레이로 검증 완료.
2. Unity Standalone 빌드(Windows/macOS)가 로컬 LAN 구조 그대로 정상 동작하는지 확인(3장 첫
   항목) — 배포 관련 코드를 하나도 안 바꾼 상태에서 먼저 "빌드가 되는가"부터 검증.
3. vision-server PyInstaller 패키징 + Unity가 로컬 서브프로세스로 자동 실행하는 기능 추가
   (1장) — 이 시점부터 "실행파일 하나면 LAN에서 바로 동작"이 완성된다. **이게 이
   배포 작업의 실질적인 종착점이다.**
4. (선택, 시간 남으면) LAN 자동 탐색 추가(2.1).
5. 빌드 파이프라인 다듬기(3장): 후처리 스크립트, 필요하면 서명.
