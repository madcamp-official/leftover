# 배포 아키텍처 설계 — 단일 실행파일 + 방코드 릴레이 (설계 단계, 미구현)

> **상태: 설계만 있고 구현 없음.** 지금 레포가 실제로 어떻게 동작하는지는
> [`게임_구동방식_정리.md`](게임_구동방식_정리.md) 1~7장(로컬 LAN, Unity 한 대)과 8장 +
> [`멀티플레이_분산_아키텍처_설계.md`](멀티플레이_분산_아키텍처_설계.md)(호스트-클라이언트
> 분산 구조, 구현 진행 중이나 LAN 전제)에 정리되어 있다. 이 문서는 그 다음 단계 —
> **"두 사람이 각자 노트북에서 실행파일 하나만 켜고, 호스트가 만든 방코드를 상대가 입력하면
> 인터넷으로 연결되어, 카메라/마이크까지 그 실행파일 하나로 처리되는" 배포 형태**를 어떻게
> 만들지에 대한 설계다. **선행 조건: 이 문서의 작업은 위 두 문서의 "로컬 LAN 호스트-클라이언트
> 구조"가 실제 플레이로 검증된 뒤에 시작한다** — 지금은 순서상 후순위.

## 0. 목표와 현재 상태의 격차

목표: Windows/macOS용 실행파일(설치 프로그램 또는 단일 exe/app) 하나를 두 사람이 각자
노트북에 받아서 실행 → 한쪽이 "방 만들기"를 누르면 방코드가 뜨고 → 다른 쪽이 그 코드를
입력하면 인터넷을 통해 연결되어 게임이 시작 → 카메라/마이크 캡처도 그 실행파일 안에서
자동으로 처리(별도 프로그램 실행 불필요).

지금과의 격차:

| 항목 | 지금 | 목표 |
|---|---|---|
| 실행 단위 | Unity 게임 + Python(`vision-server`) **두 프로세스**를 사람이 각자 수동 실행 | 실행파일 1개 |
| 연결 방식 | 호스트가 자기 **LAN IP를 직접 확인해서 알려주고**, 클라이언트가 그 IP를 입력 | **방코드** 입력 |
| 네트워크 범위 | 같은 공유기/핫스팟(**LAN**)에 있어야 함, NAT 통과 로직 없음 | **인터넷**(서로 다른 장소) |
| 카메라/마이크 | `vision-server`(Python/MediaPipe)가 캡처, Unity와 별개 | 게임 실행파일 자체가 캡처 |

## 1. 방식 A — vision-server를 게임 실행파일에 번들링 (채택)

MediaPipe 추론을 Unity(C#) 쪽으로 완전히 이식하는 대신, **이미 검증된 `vision-server`
(Python/MediaPipe) 코드를 그대로 두고 게임 실행파일이 그걸 백그라운드 프로세스로 감싸서
자동 실행/종료**한다. 프로토콜(`shared/PROTOCOL.md`, UDP 9100/9101)은 전혀 안 바뀐다 —
지금 vision-server가 `--pc-ip 127.0.0.1`로 보내는 것과 동일하게, 그냥 그 대상 프로세스를
사람이 터미널에서 켜는 대신 게임이 대신 켜줄 뿐이다.

- **패키징**: `vision-server`를 PyInstaller 등으로 OS별(Windows/macOS) 단일 실행 바이너리로
  빌드하고, 모델 파일(`models/*.task`)과 함께 Unity 빌드 결과물 옆에 동봉한다(Windows는
  `StreamingAssets` 옆 폴더, macOS는 `.app` 번들 내부 `Resources`).
- **자동 실행**: Unity가 게임 시작 시(Hub 씬에서 역할이 정해지는 시점) 이 바이너리를
  `System.Diagnostics.Process.Start`로 실행하고, `--pc-ip 127.0.0.1 --player-id p1`처럼
  로컬호스트로 인자를 넘긴다. 카메라/마이크 OS 권한 프롬프트는 이 서브프로세스 최초 실행
  시 한 번 뜨는데, 처음 켤 때 "카메라/마이크 접근 허용" 안내를 게임 UI에서 먼저 보여줘야
  프로세스가 죽은 것처럼 보이지 않는다.
- **생명주기**: 게임 종료(`OnApplicationQuit`) 시 서브프로세스도 함께 종료한다. 비정상
  종료(강제 종료, 크래시) 대비로 부모 프로세스 감시(부모 PID가 죽으면 자식도 종료) 로직이
  필요 — 자세한 값은 10장 TODO.
- **왜 이 방식인가**: MediaPipe를 Unity Sentis/Barracuda로 완전히 재구현하는 방식(문서
  초안에서 검토했던 대안)은 정확도·개발 기간 둘 다 리스크가 커서, 검증된 Python 코드를
  그대로 감싸는 이 방식을 1차 목표로 채택한다. "진짜 하나의 코드베이스"는 아니지만
  "사용자 입장에서 실행파일 하나"라는 목표는 이걸로 충분히 달성된다.

## 2. 방코드 릴레이 서버

지금 `GameEventChannel`(TCP 9200)은 호스트가 자기 IP를 화면에 띄우고 클라이언트가 그 IP를
직접 입력하는 구조([`멀티플레이_분산_아키텍처_설계.md` 5장](멀티플레이_분산_아키텍처_설계.md#5-이벤트-채널--tcp-json-라인))다.
이게 LAN 밖에서 안 되는 이유는 (1) 방코드 대신 IP를 알아야 하고, (2) 클라이언트가 인바운드
연결을 열 수 있는 공인 IP/포트가 호스트에 없으면(가정용 공유기 뒤 NAT) 애초에 연결 자체가
안 되기 때문이다. 이 두 문제를 **작은 릴레이 서버 하나**로 같이 해결한다.

### 2.1 핵심 아이디어 — 전원이 릴레이로 아웃바운드 연결

포트포워딩·NAT 홀펀칭(STUN/TURN) 같은 복잡한 방식 대신, **호스트와 클라이언트 둘 다 공인
IP를 가진 릴레이 서버로 먼저 아웃바운드 연결을 맺고, 이후 모든 트래픽을 그 연결을 통해서만
주고받는다.** 아웃바운드 연결은 일반 가정용 네트워크에서 막힐 일이 거의 없으므로, 인바운드
포트를 여는 문제 자체가 사라진다.

```
[호스트 PC] ──(아웃바운드 TCP/WebSocket)──┐
                                            ├─→ [릴레이 서버, 공인 IP]
[클라이언트 PC] ──(아웃바운드 TCP/WebSocket)┘        │
                                            방코드로 두 연결을 같은 방(room)으로 묶고
                                            그 방 안에서 온 메시지를 상대에게만 전달
```

### 2.2 흐름

1. 호스트가 "방 만들기"를 누르면 게임이 릴레이 서버에 `CREATE_ROOM` 요청 → 릴레이가 6자리
   숫자/영문 코드를 발급하고 화면에 표시.
2. 클라이언트가 그 코드를 입력해 `JOIN_ROOM(code)` 요청 → 릴레이가 같은 방으로 묶는다.
   방은 정원 2명, 코드에 유효시간(예 10분)을 둔다.
3. 이후 **`GameEventChannel`의 TCP 직접 연결 자리를, 릴레이를 경유하는 논리 채널로 그대로
   대체**한다 — 메시지 포맷(JSON 한 줄)은 그대로 두고, 전송 경로만 "직접 소켓"에서
   "릴레이 통해 상대 세션으로 전달"로 바뀐다. 게임 쪽(`GameEventChannel` 사용부)은 인터페이스가
   같으므로 미니게임 코드는 수정이 필요 없다.
4. **포즈 스트림(UDP 9100)도 릴레이가 필요하다.** 지금은 클라이언트 쪽 vision-server가
   `--pc-ip <호스트 LAN IP>`로 UDP를 직접 쏘는데, 인터넷 너머에서는 이 직접 전송이 안 된다
   (2.1과 동일한 인바운드 문제 + 대개 UDP는 더 막히기 쉬움). 가장 단순한 해법은 **포즈
   프레임도 같은 릴레이 연결(TCP/WebSocket)에 얹어 보내는 것** — 프레임이 작고(관절 13개
   + 얼굴 2개 값 JSON, 15~30fps) 오디오/비디오가 아니므로 TCP 오버헤드가 문제될 규모가
   아니다. `vision-server`의 출력을 로컬 UDP 대신 릴레이로 보내도록 바꾸는 작업이 필요하다
   (10장 TODO).
5. 로딩 화면 카메라 프리뷰(UDP 9101, 저주기 JPEG)도 같은 방식으로 릴레이하거나, 대역폭이
   부담되면 이 구간만 꺼도 된다(`--no-preview`, 이미 있는 옵션) — 필수 기능이 아니므로
   1차 구현에서는 꺼두는 것도 선택지.

### 2.3 릴레이 서버가 하지 않는 것

- **게임 로직을 전혀 모른다.** 그냥 "방코드로 묶인 두 연결 사이에서 바이트를 그대로
  전달"만 한다 — 판정/상태 관리는 여전히 호스트 Unity 프로세스가 전담한다
  ([`멀티플레이_분산_아키텍처_설계.md`](멀티플레이_분산_아키텍처_설계.md) 1장 원칙 그대로 유지).
- **음성 채팅(VoIP)을 새로 만들지 않는다.** 지금 있는 마이크 입력은 소리지르기 미니게임의
  음량 측정용(`voice.level`)이지 플레이어 간 대화가 아니다 — 이 문서의 범위 밖.
- **영상/음성 스트림 자체를 릴레이하지 않는다.** 릴레이가 나르는 건 관절 좌표 JSON과 이산
  게임 이벤트뿐, 웹캠 영상 원본이나 음성 원본은 로컬에만 있고 네트워크로 나가지 않는다
  (로딩 화면 프리뷰용 저해상도 JPEG 예외, 2.2의 5번).

### 2.4 릴레이 서버 구현 규모

"상용 배포"라고 해서 대규모 매치메이킹/로드밸런싱 인프라가 필요한 건 아니다 — 이 게임은
**동시 접속 방이 많아야 팀원들 데모용 몇 개** 수준이므로, 작은 VM/서버리스 함수 하나에
WebSocket 서버(방 생성/코드 발급/메시지 릴레이만 하는 수십~백여 줄짜리 로직)를 올리는 것으로
충분하다. 특정 클라우드/프레임워크 선택은 TODO(10장).

## 3. 빌드/배포 파이프라인 (개요, 미착수)

- **Unity 빌드**: `File > Build Settings`로 Windows(x64)/macOS(Universal) 빌드. 지금까지는
  Editor에서 Play로만 실행해봤고 Standalone 빌드 자체가 아직 한 번도 검증되지 않았다 —
  1장/2장 작업 이전에 **일단 지금 구조(로컬 LAN) 그대로 Standalone 빌드가 되는지부터
  확인**하는 게 먼저다(빌드 시 누락되는 리소스, `PoseInputHub` 등 싱글턴 초기화 순서 문제
  등은 Editor에서는 안 드러날 수 있음).
- **vision-server 바이너리 동봉**: 1.1의 PyInstaller 산출물을 Unity 빌드 폴더 구조에 맞게
  복사하는 빌드 후처리 스크립트가 필요.
- **코드사이닝/공증**: macOS는 Gatekeeper 통과를 위한 Apple Developer 서명·공증, Windows는
  SmartScreen 경고 완화를 위한 코드 서명 인증서가 있으면 좋지만, 몰입캠프 데모 규모에서는
  없어도 "고급 정보 → 실행"으로 우회 가능 — 우선순위 낮음.
- **설치 배포 방식**: zip 압축 해제형으로 시작(가장 단순), 필요하면 이후 인스톨러(Windows:
  Inno Setup 등, macOS: dmg) 검토.

## 4. 단계별 진행 순서 제안

1. **(선행)** [`멀티플레이_분산_아키텍처_설계.md`](멀티플레이_분산_아키텍처_설계.md)의
   로컬 LAN 호스트-클라이언트 구조를 실제 2대 플레이로 검증 완료.
2. Unity Standalone 빌드(Windows/macOS)가 로컬 LAN 구조 그대로 정상 동작하는지 확인(3장 첫
   항목) — 배포 관련 코드를 하나도 안 바꾼 상태에서 먼저 "빌드가 되는가"부터 검증.
3. vision-server PyInstaller 패키징 + Unity가 로컬 서브프로세스로 자동 실행하는 기능 추가
   (1장) — 이 시점부터 "실행파일 하나면 로컬 LAN에서는 동작"이 완성된다.
4. 릴레이 서버 최소 구현(방 생성/코드 발급/메시지 중계, 2.4) + `GameEventChannel`을 릴레이
   경유로 전환(2.2의 3번).
5. 포즈 스트림도 릴레이 경유로 전환(2.2의 4번) — 이 시점부터 진짜 인터넷 너머 플레이가
   가능해진다.
6. 실측 후 지연/끊김 처리 튜닝, 빌드 파이프라인 다듬기(3장).
