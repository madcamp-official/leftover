# 멀티플레이 분산 아키텍처 설계 — 호스트-클라이언트(시뮬레이션 vs 렌더링 전용)

> **상태: 설계 확정, 구현 진행 중.** 지금 레포의 실제 동작 방식(Unity 한 대 + 공용 화면)은
> [`docs/게임_구동방식_정리.md`](게임_구동방식_정리.md)에 정리되어 있다. 이 문서는 그걸
> **"한쪽 PC(호스트)가 게임 시뮬레이션 전체를 돌리고, 다른 쪽(클라이언트)은 그 결과만 받아
> 화면에 그린다"** 구조로 바꾸는 설계를 다룬다.

## 1. 핵심 모델: 호스트 = 시뮬레이션, 클라이언트 = 렌더링

이전 버전 문서는 "게임마다 로컬 판정 가능 여부가 다르다"는 전제로 미니게임별로 로컬 판정/호스트
판정을 나누려 했다. 지금은 그 구분을 없애고 훨씬 단순한 모델로 확정한다.

- **호스트 PC 하나만 게임 로직을 실행한다.** 점수, 타이머, 판정, 캐릭터 위치, 애니메이션
  상태 — 게임 상태 전부가 호스트의 `MatchController`/미니게임 스크립트 안에만 존재한다.
- **클라이언트 PC는 게임 로직을 전혀 실행하지 않는다.** 클라이언트의 미니게임 스크립트는
  입력도 안 읽고 판정도 안 하고, 호스트가 보내주는 상태/이벤트를 받아서 화면에 반영만 한다 —
  사실상 "호스트 화면을 재현하는 렌더러"다.
- 이렇게 하면 이전 문서의 가장 큰 골칫거리였던 "게임마다 로컬 판정 가능한지 표로 정리"
  (구버전 8장), "두 쪽이 각자 판정해서 디싱크 나는 문제"(구버전 2장 원칙 1)가 아예
  발생하지 않는다 — 판정을 두 번 하는 경우 자체가 없기 때문이다.

## 2. 입력은 어떻게 호스트로 모으나 — vision-server를 호스트로 겨냥

기존 구조(`게임_구동방식_정리.md` 1~3장)에서 이미 각 vision-server는 `--pc-ip <Unity PC IP>`로
어디로 쏠지 지정하게 되어 있다. 이 구조를 그대로 재사용한다.

- **P1, P2 두 vision-server 모두 호스트 PC의 LAN IP를 `--pc-ip`로 지정한다.** 클라이언트가
  자기 카메라를 처리하더라도, 인식 결과(포즈 좌표/표정)는 UDP 9100으로 클라이언트를 거치지
  않고 곧장 호스트로 간다.
- 즉 **원시 pose 스트림(UDP 9100, vision-server → 호스트)은 기존 코드를 한 줄도 안 바꾼다.**
  `PoseStreamReceiver`/`PoseInputHub`는 지금 그대로 호스트에서만 돌면 된다.
- **클라이언트 Unity 인스턴스는 vision-server 스트림을 아예 받지 않는다.** 클라이언트 쪽
  `PoseInputHub`는 항상 비어 있고, 미니게임 코드가 클라이언트 모드에서는 이걸 참조하지 않는다
  (4장).
- 부수 효과: 클라이언트 PC의 방화벽/네트워크 설정에서 UDP 9100 인바운드를 열 필요가 없어진다
  (호스트만 열면 됨). 클라이언트가 여는 건 5장의 TCP 이벤트 포트뿐이다.

```
[카메라 P1] → vision-server --player-id p1 --pc-ip <호스트 IP> ─┐
[카메라 P2] → vision-server --player-id p2 --pc-ip <호스트 IP> ─┤ UDP 9100
                                                                    ↓
                                                    호스트 Unity: 시뮬레이션 전체
                                                    (PoseInputHub, MatchController,
                                                     모든 미니게임 판정 로직)
                                                                    │
                                                     TCP 게임 이벤트 (신규, 5장)
                                                                    ↓
                                                    클라이언트 Unity: 렌더링 전용
                                                    (받은 상태를 그대로 화면에 반영)
```

## 3. 클라이언트가 받는 상태 = 이산 이벤트만

**연속 스트림이 아니라 "상태가 바뀌는 순간에만" 이벤트를 보낸다.** 캐릭터 동작이 관절 회전이
아니라 스프라이트 애니메이션이고, 판정 자체도 원래 임계값 기반 이산 판정(손 들었다/안
들었다, 머리 좌/우, 입 벌림 등)이라 이 방식이 자연스럽다. 이유 상세는 구버전 문서와 동일하되,
이제는 예외 없이 **모든 게임에 이 규칙 하나만 적용**한다(구버전 8장의 게임별 예외표는 폐기).

클라이언트가 받아야 하는 이벤트 카테고리:

- **점수/카운트 이벤트**: `score_changed(player, value)`, `hit_count(player, value)` 등 —
  숫자가 바뀔 때만.
- **타이머 이벤트**: 매 프레임 보내지 않는다. 라운드 시작 시각(호스트 기준 타임스탬프)과
  총 길이만 한 번 보내고, 클라이언트는 `남은시간 = 길이 - (지금 - 시작시각)`을 **로컬에서
  계산**해 표시한다(6장의 시계 오프셋 보정 참고). 중간에 타이머가 일시정지/리셋되는
  경우에만 갱신 이벤트를 추가로 보낸다.
- **캐릭터 상태/위치 이벤트**: 좌/우 위치 전환(`side_changed`), 점프 시작
  (`jump_started(tier)`) 같은 "상태 전환 순간"만. 이동 중인 투사체(돌, 바나나 등)처럼
  화면상 연속적으로 움직여 보여야 하는 것도 좌표를 매 프레임 보내지 않고, **발사
  시각 + 시작좌표 + 도착좌표 + 이동시간**을 한 번만 보내서 클라이언트가 그 값으로 자체
  보간(`Lerp`)한다 — 호스트가 하는 계산을 클라이언트가 그대로 재현하는 게 아니라, "무엇이
  일어났는지"만 알려주고 보여주는 방식은 클라이언트가 알아서 하는 것.
- **애니메이션 트리거 이벤트**: `throw_anim_start(player, hand, hostTime)`처럼 정해진
  스프라이트 시퀀스 재생 지시. 재생 "시작 시각"을 같이 실어 양쪽이 같은 순간에 같은 연출을
  보게 한다.
- **판정/결과 이벤트**: 명중/회피, 라운드 승자 등 — 호스트가 계산 완료한 결과값 그대로.
- **씬 전환/라운드 시작 이벤트**: 7장 참고.

**클라이언트는 이 이벤트들을 해석해서 판정을 다시 하지 않는다.** 예를 들어 "명중했다"는
이벤트를 받으면 그냥 명중 연출을 재생할 뿐, `CurrentSide(target) == lockedTargetSide`
같은 판정 로직을 클라이언트에서 다시 돌리지 않는다 — 그 로직은 호스트 전용이다.

## 4. 미니게임 스크립트 구조 — Simulate/Render 분리

각 미니게임 스크립트(`StoneThrowGame.cs` 등)를 호스트/클라이언트 겸용으로 만들기 위해, 지금
"입력 읽기 → 판정 → 연출 재생"이 한 몸으로 섞여 있는 구조를 아래 원칙으로 나눈다.

- 미니게임 스크립트는 시작 시 자기가 **호스트 모드**인지 **클라이언트 모드**인지
  `NetworkSession.Role`을 보고 분기한다(오프라인 단독 실행은 기존처럼 호스트 모드와 동일하게
  동작하되 이벤트 송신만 비활성화 — 8장 참고).
- **호스트 모드**: 지금 코드 그대로 `PoseInputHub`를 읽고 판정하고 연출을 재생하되, 상태가
  바뀌는 지점마다 3장의 이벤트를 `GameEventChannel.Send(...)`로 클라이언트에 브로드캐스트한다.
- **클라이언트 모드**: `PoseInputHub`를 절대 읽지 않는다. `Update()`에서 입력/판정 코드를
  실행하지 않고, `GameEventChannel`이 이벤트를 받을 때마다 콜백으로 화면(HUD, 캐릭터 뷰,
  투사체 연출)만 갱신한다. 연출 재생 코드(`PlayThrow`, `FlyStone` 같은 코루틴)는 호스트/
  클라이언트가 **그대로 공유**할 수 있다 — "언제, 어떤 값으로 그 코루틴을 호출하는지"만
  다르다(호스트는 판정 후 직접 호출 + 이벤트 전송, 클라이언트는 이벤트 수신 즉시 같은
  코루틴 호출).
- 이 분리 덕분에 미니게임마다 완전히 새로 짤 필요 없이, 기존 "판정 결과를 반영하는 지점"
  바로 옆에 "그 결과를 이벤트로 보낸다"만 끼워 넣고, 클라이언트 쪽엔 "이벤트 수신 → 같은
  연출 함수 호출"만 얇게 추가하면 된다.

## 5. 이벤트 채널 — TCP, JSON 라인

- **게임 이벤트 채널 = TCP.** 원시 pose 스트림(UDP, 2장)과 완전히 분리된 별도 소켓으로,
  상태 전환/판정 결과 등 이산 이벤트를 JSON 한 줄(`\n` 구분)씩 주고받는다. 이벤트 빈도가
  낮고 유실/순서보장이 필수라 TCP가 이 프로젝트 규모에 맞는 단순한 선택이다.
- **방향은 기본적으로 호스트 → 클라이언트 단방향.** 클라이언트는 화면을 그리기만 하므로
  게임 이벤트를 보낼 필요가 거의 없다. 예외는 "씬 로드 완료(ready)" 같은 7장의 확인 응답
  뿐 — 이것도 이벤트 채널을 그대로 재사용한다.
- **호스트 결정 = 수동.** 매치 시작 전 Hub 화면에서 한쪽이 "호스트로 시작"(TCP 서버 소켓을
  열고 자기 IP:포트를 화면에 표시), 다른 쪽이 그 IP를 입력해 "접속"(클라이언트로 연결)한다.
  자동 협상은 이후 UX를 다듬을 때 추가.
- **오프라인(로컬 단독 실행) 모드는 그대로 유지한다.** Hub에서 아무것도 선택하지 않고
  "시작"을 누르면 기존처럼 Unity 한 대에서 두 vision-server를 받아 혼자 돌아간다 — 개발/
  테스트, 노트북 한 대뿐인 상황에서 여전히 필요하다. 8장 참고.

## 6. 타이밍/지연 관련 체크리스트

- 판정에 순간 비교가 들어가는 게임(돌던지기 등)은 호스트 판정이라 이 문제가 원천적으로
  사라진다 — 예전 문서(구버전 6장)의 "호스트가 클라이언트 상태 이력을 버퍼로 들고 지연을
  보정"하는 문제는 **클라이언트가 아예 판정을 안 하므로 발생하지 않는다.**
- 남는 지연 문제는 "호스트에서 일어난 일을 클라이언트 화면에 얼마나 늦게 보여주느냐"뿐이다.
  타이머는 3장처럼 시작 시각 기준으로 클라이언트가 직접 계산하므로 네트워크 지연의 영향을
  받지 않는다.
- 애니메이션 동시 재생이 필요한 연출(투사체, 부메랑 등)은 이벤트에 `hostTime`(호스트 기준
  발생 시각)을 실어 보내고, 클라이언트는 수신 즉시 재생하지 않고 "호스트-클라이언트 시계
  오프셋 + 고정 버퍼"만큼 지연 후 재생한다. 시계 오프셋은 연결 시 간단한 핑퐁
  (`ping(hostTime) → pong(hostTime, clientTime)` 왕복시간의 절반)으로 추정한다.

## 6-1. 로딩 화면(캘리브레이션 대기)의 호스트-클라이언트 처리

`LoadingScreenController`는 씬 로드 중 캘리브레이션을 기다리는 화면이고,
`SceneFadeTransition`이 `IsReady`가 설 때까지 씬 전환을 붙잡는다. 그런데 클라이언트의
`PoseInputHub`는 구조상 항상 비어 있으므로(2장) `AreBothCalibrated`가 영원히 false여서
**클라이언트가 로딩 화면에서 빠져나오지 못한다**(실측으로 확인된 문제). 그래서:

- **캘리브레이션 판정도 호스트 전담이다.** 호스트가 `loading_status` 이벤트로 양쪽의
  추적/캘리브레이션 상태·진행률·프리뷰 연결 여부와 함께 자신의 `ready` 값을 보내고,
  클라이언트는 자기 판단 없이 그 `ready`를 그대로 쓴다.
- **카메라 프리뷰는 호스트가 중계한다.** vision-server는 프리뷰(UDP 9101)도 호스트로만
  보내므로, 호스트가 받은 JPEG를 `loading_preview` 이벤트(base64)로 클라이언트에 넘긴다.
  클라이언트는 `CameraPreviewReceiver.ApplyRelayedFrame()`으로 주입해 UDP로 직접 받은 것과
  똑같은 디코딩/스테일 판정 경로를 태운다. 중계로 들어온 프레임은 다시 중계하지 않는다
  (에코 루프 방지).
- **주의(실제로 걸렸던 함정)**: 상태 전송을 스로틀(10Hz)하면 `ready`가 true로 바뀐 프레임에
  전송이 밀릴 수 있고, 호스트는 곧 로딩 화면을 닫아 더는 상태를 보내지 않으므로 클라이언트가
  `ready=true`를 영원히 못 받는다. `ready` 값이 **바뀌는 순간에는 스로틀을 무시하고 즉시
  전송**해야 한다. 또 라운드마다 중계 상태를 비워야(`Show()`) 지난 라운드의 `ready=true`가
  남아 클라이언트가 새 캘리브레이션을 건너뛰는 일이 없다.

## 7. 씬 전환/라운드 시작 동기화 — ready-check 게이트

기존 `MatchController.LoadNextRound`는 로컬에서 바로 다음 씬을 로드하지만, 분산 구조에서는
호스트가 전환을 결정한 시점과 클라이언트가 실제로 씬 로드를 마치는 시점 사이에 네트워크 지연
+ Unity 씬 로드 시간 차이가 생긴다. 호스트가 이미 라운드를 시작했는데 클라이언트가 아직
로딩 중이면, 클라이언트 화면에서는 시작 이벤트를 놓치거나 늦게 반영된다.

```
호스트: 라운드 N 종료 판정 → "다음 라운드: StoneThrow" 이벤트 브로드캐스트
  ├─ 호스트: 자기 화면에 씬 로드 시작, 로딩/대기 화면 표시
  └─ 클라이언트: 이벤트 수신 → 씬 로드 시작, 동일한 로딩/대기 화면 표시
                → 로드 완료되면 "ready" ack를 호스트로 전송
호스트: 자기 로드 완료 + 클라이언트 ready ack 둘 다 받으면
  → "라운드 시작" 이벤트(공통 타임스탬프 포함) 브로드캐스트
  → 양쪽 다 이 시점에 대기 화면을 내리고 실제 라운드(타이머/판정) 시작
(타임아웃: 일정 시간(예 5초) 내 ready가 안 오면 재연결 대기 화면으로 전환 — 9장 연결
 끊김 처리와 동일 패턴 재사용)
```

- 이미 있는 `SceneFadeTransition`(페이드 인/아웃)을 이 대기 시간을 가리는 용도로 그대로
  활용한다 — 페이드가 걸려 있는 동안 ready-check가 끝나길 기다리면 자연스러운 연출처럼
  보인다.
- 호스트 자신의 로드가 클라이언트보다 항상 먼저 끝난다는 보장이 없으므로, "호스트가 끝나면
  바로 시작"이 아니라 반드시 **양쪽 ready 확인 후 시작**이어야 한다.
- **씬 로드뿐 아니라 "게임 내 캘리브레이션"도 같은 게이트가 필요하다.** 과일따기(점프
  기준선), 돌던지기(얼굴·양손 차렷 자세 중립값) 모두 캘리브레이션을 거치는데, 이건 오직
  **호스트에서만** 일어난다(클라이언트는 카메라 입력 자체가 없으므로 — 2장). 클라이언트는
  캘리브레이션 진행 상태를 이벤트로 받아 "대기 중..." 화면만 보여주면 되고, 호스트의
  캘리브레이션이 끝나는 순간 곧바로 매치 타이머를 시작해도 된다(클라이언트가 별도로 완료할
  것이 없으므로 이전 버전 문서의 "양쪽 다 완료 확인" 로직은 필요 없어짐 — 구조 단순화의
  또 다른 효과).

## 8. 연결 끊김 처리 / 오프라인 모드

- 원시 pose 스트림(UDP)은 기존 규칙(0.5초 이상 미수신 시 "연결 끊김") 유지 — 호스트에서만
  일어나는 일이라 이 부분은 전혀 안 바뀐다.
- TCP 이벤트 채널이 끊기면(소켓 종료 감지 또는 일정 시간 하트비트 미수신) 클라이언트는
  "호스트 연결 끊김 — 재연결 대기 중" 화면으로 전환한다. 호스트는 클라이언트 끊김을
  감지하면 진행 중인 라운드를 일시정지하고 같은 재연결 대기 상태로 전환한다(7장 대기 화면
  재사용).
- **타임아웃이 아예 없는 게임 상태를 특히 주의할 것.** 돌 or 바나나의 `WaitingThrow`(던지는
  사람 차례)는 의도적으로 무한 대기가 설계다([05_돌or바나나.md](minigames/05_돌or바나나.md)
  10장/13장). 이 경우도 호스트 로직 자체는 안 바뀌지만(호스트가 그 상태를 갖고 있으므로),
  TCP 연결이 끊긴 채로 방치되면 클라이언트만 영원히 멈춘 화면을 보게 되니 하트비트 기반
  끊김 감지가 별도로 필요하다.
- **오프라인 모드(Unity 한 대, 네트워크 없음)는 계속 지원한다.** `NetworkSession.Role ==
  Offline`이면 모든 미니게임이 지금처럼(호스트 모드와 동일 코드 경로, 단 이벤트 송신만
  no-op) 동작한다 — 개발 중 테스트나 노트북 한 대짜리 데모에 필요.

## 9. 구현 순서

1. **네트워크 기반 레이어** (`Assets/Scripts/Network/`): `NetworkRole`/`NetworkSession`
   싱글턴(호스트 대기/클라이언트 접속, 연결 상태), `GameEventChannel`(TCP 연결 수립, JSON
   라인 직렬화/역직렬화, 백그라운드 스레드 수신 → 메인 스레드 큐 디스패치, 끊김 감지).
2. **Hub 화면에 호스트/접속 UI 추가**, `MatchController`가 `NetworkSession.Role`에 따라
   라운드 전환/결과를 이벤트로 브로드캐스트하도록 확장 — 7장 ready-check 게이트 포함.
3. **미니게임별 Simulate/Render 분리 적용** (4장 패턴) — 로컬 판정이든 상대 상태가
   필요한 판정이든 이제 전부 "호스트가 판정, 클라이언트는 이벤트 재생"으로 동일하게
   처리하므로 게임마다 특별 케이스를 고민할 필요가 줄었다. 구현 순서는 이벤트 종류가 가장
   단순한 게임(과일따기·코코넛깨기: 점수 이벤트 위주)부터 시작해, 타이밍이 중요한 게임
   (돌던지기: 애니메이션 트리거 + 투사체 보간)으로 진행.
4. 시계 오프셋 보정(6장), 재연결 처리(8장) 다듬기.
