# 멀티플레이 분산 아키텍처 설계 (진행 중 — 각자 화면 버전)

> **상태: 설계 단계, 미구현.** 지금 레포의 실제 동작 방식(Unity 한 대 + 공용 화면)은
> [`docs/게임_구동방식_정리.md`](게임_구동방식_정리.md)에 정리되어 있다. 이 문서는 그걸
> **"두 사람이 각자 자기 화면에서 플레이"** 하는 구조로 바꿀 때의 설계를 다룬다 — 아직 코드는
> 안 바뀌었고, 미니게임 세부 규칙을 잡아가면서 참고할 원칙/체크리스트로 우선 정리한다.

## 1. 왜 이렇게 바꾸나

기존 구조는 Unity 프로세스 하나가 두 vision-server의 pose 스트림을 받아 판정·렌더링을 전부
전담하고, 두 사람은 그 화면 하나를 같이 보는 방식이었다(자세한 배경은
[게임_구동방식_정리.md 2장](게임_구동방식_정리.md#2-멀티플레이의-실체--로컬-협업-관전--분산-입력)).
이제 **화면도 각자** 가져야 하므로, Unity 인스턴스가 PC마다 하나씩(총 2개) 떠서 서로 네트워크로
동기화해야 한다.

## 2. 기본 원칙

1. **판정은 한쪽(호스트)만 계산한다.** 여러 미니게임이 "그 순간 상대가 어떤 상태였는가"를
   비교해야 승패가 갈리므로(돌던지기 명중 판정 등), 양쪽이 각자 판정을 복제 계산하면 미세한
   타이밍 차이로 디싱크가 난다. 호스트가 유일한 권위(authority)를 갖는다.
2. **동기화 payload는 대부분 "상태 전환 이벤트"다, 연속 스트림이 아니다.** 캐릭터 동작이
   관절 회전이 아니라 스프라이트 애니메이션으로 구성되고 있고, 게임 로직 자체도 원래 임계값
   기반 이산 판정(손 들었다/안 들었다, 머리 좌/우, 입 벌림 등)이라, "상태가 바뀌는 순간에만"
   보내면 된다. 매 프레임 값을 계속 보낼 필요가 없다 — 이게 이 구조를 event-log 방식에 가깝게
   만드는 핵심 전제다.
3. **원시 pose 스트림(vision-server → Unity)은 지금 그대로 UDP.** 이건 "최신 값이 곧 진실"이라
   중간에 유실돼도 다음 프레임이 덮어쓰므로 문제없다. 반면 4장의 "게임 이벤트"는 성격이 달라서
   별도 채널/보장이 필요하다.
4. **판정에 상대방 상태가 필요 없는 게임은 호스트 개입 없이 각자 로컬에서 판정한다.**
   `docs/minigames/`의 실제 세부 규칙을 보면 6개 중 절반 이상이 "자기 자신의 포즈만으로
   끝나는" 판정이다(과일따기: 자기 점프+입벌림, 코코넛깨기: 자기 손-머리 거리, 눈빛싸움: 자기
   EAR). 이런 게임은 그 플레이어의 로컬 PC(자기 카메라를 처리하는 쪽)가 판정까지 끝내고
   **결과 이벤트만**(`fruit_scored: tier=1`, `hit_count: 7` 등) 호스트로 보내면 된다 — 굳이
   원시 상태를 호스트로 보내 다시 판정할 필요가 없고, 6장의 타임스탬프 보정 문제도 아예
   생기지 않는다. 반대로 **상대방 상태와 동시 비교가 필요한 게임**(돌던지기 명중/회피, 자세
   따라하기 실루엣 매칭, 돌 or 바나나 던지기/받기)은 반드시 호스트가 양쪽 원시 상태를 받아
   판정해야 한다 — 8장 표에서 게임마다 어느 쪽인지 구분해뒀다.

## 3. 이벤트 채널 vs 원시 pose 채널 (신뢰성 요구사항이 다르다)

| | 원시 pose 스트림 (기존, 유지) | 게임 이벤트 (신규) |
|---|---|---|
| 전송자 | 각 vision-server → 자기 로컬 Unity | 호스트 Unity ↔ 클라이언트 Unity |
| 성격 | 연속, "최신 값이 진실" | 이산, "상태 전환 하나하나가 진실" |
| 유실 허용 | 됨 (다음 프레임이 대체) | **안 됨** — 하나 유실되면 그 전환 자체가 사라짐 |
| 순서 뒤바뀜 허용 | 됨 | **안 됨** — 턴 전환/판정 순서가 꼬이면 상태 모순 발생 |
| 권장 방식 | 지금처럼 순수 UDP | 시퀀스 번호 + ack/재전송을 얹은 UDP, 또는 TCP |

**체크포인트**: 미니게임 세부 규칙을 잡을 때, 그 게임에서 나오는 이벤트가 "유실되면 눈에 띄게
망가지는" 종류인지 항상 확인할 것(턴 상태, 판정 결과, 씬 전환은 전부 해당).

## 4. 이벤트 타입 분류

- **상태-전환 이벤트** (가장 흔함): `hand_raised: right`, `head_tilt: left`, `mouth_open: true`,
  `jump_tier: 2` 등. 로컬에서 `PoseInputHub` 해석 결과가 바뀌는 순간에만 발생.
- **애니메이션 트리거 이벤트**: `throw_anim_start(hand=right, t=host_time)`처럼, 캔에 정해진
  스프라이트 시퀀스 재생을 지시. 재생 시작 "시각"을 같이 실어서 양쪽 화면이 같은 순간에
  같은 연출을 보게 한다(7장 참고).
- **포즈 스냅샷 이벤트** (예외 케이스, 자세따라하기 전용): 캡처된 순간의 관절 13개 좌표
  전체를 한 번에 담아 보내는 이벤트. 이 미니게임만 실루엣 모양 자체(연속 좌표)가 판정에
  필요해서, "이산 이벤트만 보낸다"는 2장 원칙의 유일한 예외다. 빈도가 낮아(포즈 지정 턴마다
  1회) 대역폭 문제는 없음.
- **판정/결과 이벤트**: 호스트가 계산한 명중/회피, 득점, 사이클 카운트, 라운드 승자 등. 호스트→
  양쪽 클라이언트로 브로드캐스트.
- **턴/페이즈 이벤트**: 돌 or 바나나처럼 역할이 번갈아 바뀌는 게임 전용 — "지금 누구 턴, 어느
  서브페이즈(던지기/받기/부메랑복귀)"를 호스트가 단독 소유하고 통지. 클라이언트는 절대 로컬
  판단으로 턴을 앞당기지 않는다.
- **씬 전환 이벤트**: 5장 참고.

## 5. 씬 전환 동기화 — 로딩(대기) 화면이 필요한가

**필요하다.** 이유:

- 지금 코드(`MatchController.LoadNextRound`)는 로컬에서 바로 다음 씬을 로드하지만, 분산
  구조에서는 호스트가 전환을 결정한 시점과 클라이언트가 실제로 씬 로드를 마치는 시점 사이에
  네트워크 지연 + Unity 씬 로드 시간(기기마다 다를 수 있음) 차이가 생긴다.
- 한쪽이 이미 다음 미니게임을 시작해서 라운드 타이머/판정이 돌아가는데, 다른 쪽은 아직 씬
  로딩 중이면 "상대 없이 혼자 시작한 라운드"가 되어 불공정하고, 포즈 스트림도 아직 준비 안 된
  상태에서 판정이 시작될 수 있다.

**권장 흐름 (ready-check 게이트)**:

```
호스트: 라운드 N 종료 판정 → "다음 라운드: StoneThrow" 이벤트 브로드캐스트
  ├─ 호스트: 자기 화면에 씬 로드 시작, 로딩/대기 화면 표시
  └─ 클라이언트: 이벤트 수신 → 씬 로드 시작, 동일한 로딩/대기 화면 표시
                → 로드 완료되면 "ready" ack를 호스트로 전송
호스트: 자기 로드 완료 + 클라이언트 ready ack 둘 다 받으면
  → "라운드 시작" 이벤트(공통 타임스탬프 포함) 브로드캐스트
  → 양쪽 다 이 시점에 대기 화면을 내리고 실제 라운드(타이머/입력 판정) 시작
(타임아웃: 일정 시간(예 5초) 내 ready가 안 오면 재연결 대기 화면으로 전환 — 6장 연결
 끊김 처리와 동일 패턴 재사용)
```

- 이미 있는 `SceneFadeTransition`(페이드 인/아웃)을 이 대기 시간을 가리는 용도로 그대로
  활용할 수 있다 — 페이드가 걸려 있는 동안 ready-check가 끝나길 기다리면, 사용자 입장에서는
  "부자연스러운 멈춤"이 아니라 원래 있던 연출처럼 보인다. 즉 완전히 새로운 화면을 만들기보다
  **기존 페이드 트랜지션을 ready-check 대기와 겹쳐서 쓰는 방식**을 우선 검토할 것.
- 호스트 자신의 로드가 클라이언트보다 항상 먼저 끝난다는 보장이 없으므로, "호스트가 끝나면
  바로 시작"이 아니라 반드시 **양쪽 ready 확인 후 시작**이어야 한다.
- **씬 로드뿐 아니라 "게임 내 캘리브레이션"도 같은 게이트가 필요하다.** 과일따기는 시작 시
  `JumpHeightCalibrator`가 P1/P2 각각 1.5초씩 기준선을 잡고, **양쪽 다 끝나야** 매치 타이머와
  점수 판정이 시작된다([03_과일따기.md](minigames/03_과일따기.md) 3장). 지금은 한 Unity
  안에서 두 캘리브레이터가 같은 프레임에서 값을 보고 있어 자동으로 맞춰지지만, 분산 구조에서는
  "내 캘리브레이션 완료" 이벤트를 서로 보내고 호스트가 **둘 다 완료 확인 후에만** "매치 시작"
  이벤트를 브로드캐스트해야 한다 — 씬 전환 ready-check와 동일한 패턴이므로 같은 구현을
  재사용할 것. 이후 다른 미니게임에 캘리브레이션 단계가 추가되면 전부 이 패턴을 따른다.

## 6. 타이밍/지연 관련 체크리스트

- 판정에 순간 비교가 들어가는 게임(돌던지기 등)은 이벤트에 발생 시각(host 기준 또는 각자
  타임스탬프 + 오프셋 보정)을 실어서, 네트워크 지연 때문에 "억울한 판정"이 나지 않게 한다.
- 양쪽 화면에 동시에 보여야 하는 연출(투사체, 다가오는 벽, 바나나 부메랑)은 수신 즉시 재생하지
  않고 "host_time + 고정 버퍼"로 예약 재생해서 화면 간 타이밍 차이를 줄인다.
- **호스트는 "가장 최근에 받은 값"이 아니라 "그 판정 시점의 값"을 봐야 한다.** 돌던지기가
  전형적인 예: 발사 판정은 P1 로컬에서 도는 타이머가 스스로 정하고([01_돌던지기.md](minigames/01_돌던지기.md)
  3장 — 이 타이머 자체는 손 상태 전환 이벤트 두 개만 있으면 호스트가 재현 가능해 네트워크
  친화적이다), 그 발사 "순간" 상대(P2)의 머리 기울기가 어땠는지를 비교해야 명중/회피가
  갈린다. 이때 호스트가 그 순간 P2에게서 아직 최신 머리-기울기 이벤트를 못 받은 상태일 수
  있으므로, 단순히 "지금까지 들어온 P2의 마지막 값"을 쓰면 네트워크 지연만큼 판정이 어긋날 수
  있다. **상태-전환 이벤트에 발생 시각을 실어 두고, 호스트가 플레이어별로 짧은(예: 최근
  0.5~1초) 시간별 상태 이력을 버퍼로 들고 있다가, 판정 시점에 "그 시각 기준 값"을 조회하는
  방식**을 권장한다 — 단순 최신값 참조보다 공정하다.

## 7. 연결 끊김 처리

- 원시 pose 스트림은 기존 규칙(0.5초 이상 미수신 시 "연결 끊김") 유지.
- 상대 PC와의 게임 이벤트 채널 자체가 끊겼을 때(라운드 진행 중)의 동작(일시정지/기권/재연결
  대기 화면)은 아직 미정 — 5장의 ready-check 대기 화면과 같은 UI를 재사용해 "재연결 대기 중"
  상태로 전환하는 안을 우선 후보로 검토.

## 8. 미니게임별 예외/주의사항 메모

| 미니게임 | 판정 방식 | 이 구조에서 특별히 걸리는 점 |
|---|---|---|
| 돌던지기 | 호스트 판정(상대 상태 필요) | ① 발사 타이머 자체는 손 상태 전환 이벤트만으로 호스트가 재현 가능(네트워크 친화적). ② 다만 "발사 순간 상대 머리 기울기"는 6장의 타임스탬프 이력 조회가 필요. ③ [01_돌던지기.md 5장](minigames/01_돌던지기.md)의 분할 화면(상대 앞모습/자기 뒷모습) 목표 구도는 **"각자 화면"에서는 좌/우 절반을 다 그릴 필요 없이 자기 쪽 절반만 풀스크린으로 그리면 되는 것으로 재정의 가능** — 다만 그러려면 상대 캐릭터의 실시간 애니메이션 상태(포즈/표정/발사 동작)가 계속 이벤트로 넘어와야 자기 화면에 상대를 그릴 수 있음(아래 공통 주의 참고) |
| 자세 따라하기 | 호스트 판정(상대 상태 필요) | 포즈 스냅샷 이벤트(연속 좌표 통째로) 필요 — 4장의 유일한 예외 |
| 점프해서 과일따기 | **로컬 판정 가능** | 판정/점수가 플레이어별 완전 독립이라([03_과일따기.md](minigames/03_과일따기.md) 3장) 각자 PC가 직접 판정하고 결과 이벤트만 보내면 됨. 다만 **캘리브레이션 완료 동기화**(양쪽 다 끝나야 매치 타이머 시작)는 새로 필요 — 5장에 추가한 ready-check 패턴 참고 |
| 머리로 코코넛 깨기 | **로컬 판정 가능** | 사이클 카운트도 완전 개별 처리라([02_머리로코코넛깨기.md](minigames/02_머리로코코넛깨기.md) 3장) 로컬 판정 + 결과 이벤트만으로 충분 — 리스크 낮음 |
| 돌 or 바나나 | 호스트 판정(상대 상태 필요) | 턴/서브페이즈(부메랑 포함) 소유권을 호스트가 단독으로 가져야 함 |
| 눈빛 싸움 | 로컬 계산 + 호스트 비교 | 각자 EAR 지속시간(0.4초) 판정은 로컬에서 하고 "눈 감음 확정" 이벤트만 보내면 되지만, **먼저 감은 쪽이 패배**라는 승패 자체는 두 이벤트의 도착 순서가 아니라 6장처럼 타임스탬프 기준으로 호스트가 비교해야 함(동시에 감았다고 느껴도 네트워크상 도착 순서는 뒤바뀔 수 있음) |

**공통 주의(로컬 판정 게임이라도)**: 판정은 로컬에서 끝나더라도, 화면에 상대 캐릭터가 같이
보이는 구도라면(과일따기·코코넛깨기 모두 현재 구도상 좌우에 양쪽 캐릭터가 함께 보임 —
[03_과일따기.md 5장](minigames/03_과일따기.md#5-화면-구도), [02_머리로코코넛깨기.md 5장](minigames/02_머리로코코넛깨기.md#5-화면-구도))
**애니메이션 트리거 이벤트(4장)는 여전히 상대 화면으로 보내야 한다** — "판정에 상대 상태가
필요 없다"는 것과 "상대 화면에 내 동작을 안 보여줘도 된다"는 것은 별개다.
