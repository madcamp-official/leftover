# 통신 프로토콜 스펙 (v1.1 — 우가우가게임, 연속 스트리밍)

> 이전 버전(v0.3)은 3D 검투 게임용으로, MediaPipe가 동작을 분류해서 "인식된 동작 이벤트"
> 하나만 이산적으로 보내는 구조였다. 이번 게임은 미니게임들이 저마다 다른 방식으로
> 관절 좌표를 해석해야 해서(예: 손 든 상태는 돌던지기·돌바나나 둘 다 쓰지만 임계값이 다를 수
> 있음), 분류를 vision-server가 미리 끝내지 않고 **원시 관절 좌표를 매 프레임 그대로 스트리밍**
> 하고 Unity 쪽에서 게임별로 해석한다. 눈 감김/입 벌림처럼 게임과 무관하게 보편적인 두 값만
> vision-server가 미리 계산된 비율로 얹어서 보낸다 (모든 게임이 매번 같은 눈 랜드마크
> 인덱스/EAR 공식을 다시 구현할 필요가 없도록).
>
> **v1.2 계획(미구현)**: 새 미니게임 [7. 소리지르기](../docs/minigames/07_소리지르기.md)가
> 마이크 음량만 입력으로 쓰기 때문에, 아래 "계획 중: 마이크 음량(`voice`) 필드" 절에 정의한
> `voice.level` 필드를 프레임 메시지에 추가할 계획이다. 아직 vision-server도 Unity도 이
> 필드를 주고받지 않는다 — 실제 구현 전까지는 설계 스케치로만 남겨둔다.
>
> **v1.1 변경**: 실측 결과 카메라 1대 앞에 두 사람을 같이 세우면(v1.0 전제) 붙어 있을 때
> 한쪽이 인식 안 되는 문제가 나와서, **플레이어 1명당 카메라 1대(온라인 모드)를 기본으로
> 바꿨다**. JSON 메시지 포맷 자체는 안 바뀌었고(`players` 배열에 한 명만 담겨서 오는 게
> 더 흔해졌을 뿐), id 배정 방식만 두 모드로 나뉜다 — 아래 "좌/우 플레이어 구분" 참고.

## 포트

| 용도 | 포트 | 방향 |
|---|---|---|
| 연속 프레임 스트림 (포즈+얼굴) | UDP 9100 | vision-server(Python) → PC(Unity) |

포트 하나로 통일 — 폰 IMU/시간동기화(구 버전의 9000/9001)는 이번 게임에서 쓰지 않는다(웹캠
단독 인식, 폰 없음). **온라인 모드**에서는 vision-server 인스턴스 두 개(플레이어별 노트북
각각)가 전부 이 포트로 같은 Unity PC를 향해 쏘지만, 서로 다른 소스에서 보내는 UDP 데이터그램
이라 Unity 쪽에서 포트를 나눌 필요는 없다 — 각 패킷의 `players[].id`로만 구분됨.

## 좌/우 플레이어 구분

두 가지 실행 모드가 있고, id 배정 방식이 다르다 (`vision-server/main.py`, `--player-id` 옵션):

- **온라인 모드(권장, `--player-id` 지정)**: 플레이어 1명당 카메라 1대. 각 vision-server
  인스턴스가 자기 카메라에 잡힌 첫 사람을 실행 인자로 받은 id(`p1` 또는 `p2`)로 고정해서
  보낸다 — 애초에 한 프레임에 한 명만 잡히므로 좌/우 정렬이 필요 없다. 실측 결과 카메라
  1대에 두 사람을 같이 세우면 붙어 있을 때 사람 감지 NMS가 한쪽을 억제해버리는 문제가
  확인되어(구모드 문제 참고) 이 방식을 기본으로 채택했다.
- **구모드(`--player-id` 생략, 카메라 1대에 두 사람)**: 한 프레임에 두 사람이 잡히면, 직전
  프레임에서 각 id가 있던 hip 중심 x좌표에 더 가까운 쪽으로 매칭한다(이력 기반 최근접
  매칭 - `_assign_player_ids`). 최초 프레임이나 이력이 없으면 작은 쪽(화면 왼쪽)을 `p1`,
  큰 쪽을 `p2`로 배정. 단순 x좌표 정렬(v1.0 초기 방식)은 두 사람이 순간적으로 겹치거나
  교차하면 hip x좌표 대소관계가 역전돼 라벨이 프레임 단위로 뒤바뀌는 문제가 실측으로
  확인되어 이력 기반 매칭으로 교체했다. 장비가 카메라 한 대뿐일 때 빠른 테스트 용도로는
  여전히 쓸 수 있지만, 두 사람이 붙어 있으면 인식 자체가 누락되는 문제까지는 해결하지
  못해(사람 감지 신뢰도 임계값을 0.5→0.3으로 낮춰도 완전히 해소되진 않음) 데모용 기본
  모드로는 온라인 모드를 쓴다.

두 모드 모두 와이어 포맷(JSON 스키마)은 동일 — Unity 쪽(`PoseStreamReceiver`/`PoseInputHub`)은
어느 모드로 보내든 수정 없이 그대로 받는다. 온라인 모드에서는 두 vision-server 인스턴스가
각각 `players` 배열에 자기 담당 플레이어 한 명만 담아 보내고, `PoseInputHub.ApplyFrame()`이
프레임마다 들어온 id만 갱신하는 구조라 두 스트림이 자연스럽게 합쳐진다.

## 메시지 포맷

매 프레임(웹캠 캡처+추론 루프 속도 그대로, 목표 없음 — 대략 15~30fps) 아래 JSON 하나를
UDP로 보낸다. 사람이 한 명만 잡히면 `players` 배열에 한 개만, 아예 안 잡히면 빈 배열로 보낸다
(Unity 쪽은 없는 플레이어의 이전 프레임 값을 유지하되, 일정 시간(기본 0.5초) 이상 안 보이면
"연결 끊김"으로 취급해야 함).

```json
{
  "t": 1721234567.123,
  "players": [
    {
      "id": "p1",
      "pose": {
        "nose": {"x": 0.31, "y": 0.22},
        "leftShoulder": {"x": 0.28, "y": 0.35}, "rightShoulder": {"x": 0.40, "y": 0.35},
        "leftElbow": {"x": 0.22, "y": 0.48}, "rightElbow": {"x": 0.46, "y": 0.48},
        "leftWrist": {"x": 0.18, "y": 0.30}, "rightWrist": {"x": 0.50, "y": 0.60},
        "leftHip": {"x": 0.30, "y": 0.62}, "rightHip": {"x": 0.38, "y": 0.62},
        "leftKnee": {"x": 0.29, "y": 0.80}, "rightKnee": {"x": 0.39, "y": 0.80},
        "leftAnkle": {"x": 0.28, "y": 0.97}, "rightAnkle": {"x": 0.40, "y": 0.97}
      },
      "face": {
        "mouthOpenRatio": 0.08,
        "eyeAspectRatio": 0.29
      }
    },
    {
      "id": "p2",
      "pose": { "...": "위와 동일한 13개 키" },
      "face": { "mouthOpenRatio": 0.02, "eyeAspectRatio": 0.30 }
    }
  ]
}
```

### `pose` 필드 (13개 관절, 전부 필수)

MediaPipe Pose Landmarker의 33개 랜드마크 중 상/하체 게임에 실제로 쓰는 13개만 추린 것.
좌표는 **MediaPipe 정규화 이미지 좌표** 그대로: `x`는 0(왼쪽)~1(오른쪽), `y`는 0(위)~1(아래).
Unity 쪽에서 화면/월드 좌표로 변환할 때 y축 방향이 뒤집힌다는 것(이미지는 아래로 증가, Unity
월드는 보통 위로 증가)을 잊지 말 것. z(깊이)는 노이즈가 커서 이번에도 안 보낸다 — 점프 높이처럼
깊이가 필요해 보이는 값도 전부 y좌표 변화량으로 근사한다(자세한 계산은 Unity
`Assets/Scripts/Common/GestureRecognizer.cs` 참고).

| 키 | 용도 |
|---|---|
| `nose` | 머리 기울기(돌바나나 회피) |
| `leftShoulder`/`rightShoulder` | 팔 각도 계산 기준점(손 들기 판정 등) |
| `leftElbow`/`rightElbow` | 팔 각도(캐릭터 관절 리깅) |
| `leftWrist`/`rightWrist` | 손 들기 판정(돌던지기, 돌바나나) |
| `leftHip`/`rightHip` | P1/P2 좌우 구분 기준, 점프 높이 계산의 몸통 중심 |
| `leftKnee`/`rightKnee` | *(현재 미사용)* 자세따라하기(PoseCopy) 전용이었으나 그 게임이 폐기되어 지금은 어떤 미니게임도 이 값을 읽지 않는다 — 프로토콜 스키마 호환을 위해 필드 자체는 유지 |
| `leftAnkle`/`rightAnkle` | 점프 높이 계산(기준선 대비 변화량) |

### `face` 필드 (2개 값, vision-server가 미리 계산해서 보냄)

| 키 | 범위/의미 |
|---|---|
| `mouthOpenRatio` | 0에 가까움=다묾, 커질수록 크게 벌림. 입술 상하 랜드마크 간격을 얼굴 크기로 정규화한 값 |
| `eyeAspectRatio` (EAR) | 뜬 눈은 보통 0.25~0.35, 감으면 0.1 이하로 급격히 떨어짐. 표준 6점 EAR 공식 사용 |

이 두 값에 대한 임계값(예: "몇 이하면 감은 것으로 볼지")은 **Unity 쪽에서** 게임별로 정하고,
필요하면 게임 시작 시 짧게 "눈 크게 뜨기/입 다물기" 캘리브레이션을 거쳐 사람마다 보정한다 —
vision-server는 원값만 보내고 판정 임계값을 갖지 않는다.

## 계획 중: 마이크 음량(`voice`) 필드 — 소리지르기용, 미구현

[7. 소리지르기](../docs/minigames/07_소리지르기.md)는 관절/얼굴 좌표를 전혀 쓰지 않고 마이크
음량만 본다. 온라인 모드에서는 각 플레이어의 vision-server가 이미 그 사람의 PC에서 카메라와
함께 돌고 있으므로, 같은 프로세스가 시스템 기본 마이크도 같이 캡처해서 같은 프레임 메시지에
아래처럼 `voice` 필드를 추가로 얹어 보내는 것을 제안한다(별도 포트/프로세스 불필요):

```json
{
  "id": "p1",
  "pose": { "...": "기존 13개 키 그대로" },
  "face": { "mouthOpenRatio": 0.08, "eyeAspectRatio": 0.29 },
  "voice": { "level": 0.42 }
}
```

| 키 | 범위/의미 |
|---|---|
| `voice.level` | 0(무음)~1(설계상 최대 음량)로 정규화된 순간 음량. RMS를 dB로 바꾼 뒤
  일정 범위(예: 무음 -60dB ~ 최대 0dB)를 0~1로 클램프하는 방식을 제안 — 정확한 매핑 공식과
  마이크 기종/거리 편차 보정 필요 여부는 아래 "결정 필요"에 미해결로 남긴다. |

`pose`/`face`와 마찬가지로 이 값도 vision-server가 분류나 판정 없이 원값(정규화된 순간
음량)만 보내고, "턴 동안의 최댓값" 같은 게임별 해석은 전부 Unity 쪽(`ScreamDuelGame`)이
담당한다 — 이 프로젝트의 다른 모든 신호와 같은 원칙.

## Unity 수신부

`pc-game/Assets/Scripts/Common/PoseStreamReceiver.cs`가 이 포맷을 파싱해서
`PoseInputHub`(같은 폴더)에 채워 넣는다. 개별 미니게임은 `NetworkInputProvider`/UDP를 직접
몰라도 되고, `PoseInputHub.GetPlayer(PlayerId.P1)`처럼 정리된 API만 사용한다 — 자세한 계약은
`pc-game/Assets/Scripts/Common/README.md` 참고.
